# API Reference — Rizin

Which routes the RIZIN tab serves on port 9000, from opening a file to the
emulation, its breakpoints and its patches.

These 37 rows, for 32 routes, stood in [API Reference](api.md) until they were
59% of that page and it reached the documentation website's cap of 100,000
characters per page. The promise did not change, it spans both pages now: every
route of `webui/app.py` has exactly one row, on exactly one of them
(`tests/test_docs.py::test_api_page_documents_every_route_and_nothing_else`).

One rizin session per opened file and browser tab (RIZIN tab). Addresses are integers in answers, except the machine words of the emulation routes (`pc`, the registers, the stack, the assistant's offered `value`), which are exact `"0x…"` strings (see the emulation rows); in requests `addr` is decimal or `0x…`. Errors: 400 `{"refused": reason}` for invalid input, a refused console command or a file that cannot be opened (missing, empty, a folder); 403 for a UNC path or a path outside the folders that `/api/file/download` serves too (which include the uploads in `%TEMP%\rizin_uploads`); 404 `{"error": "session ended"}` (with `reason` when rizin stopped during that request); 409 `{"busy": true, "step"}` while an analysis step or another request has rizin (views wait about 2 s first), `{"moved": true}` once the file was opened in another tab, or `{"superseded": true}` for an open that a newer open of the same tab overtook; 500 `{"error"}` when rizin could not open the file ("rizin could not open the file: …"), answered something unexpected ("rizin answered something unexpected: …") or answered one of the three lists that are filtered on the server (strings, imports, flag names) with more than 32 MB ("too many strings to list here …: filter them in the console") or answered more than the limit of the command it ran ("rizin's answer to pdfj is larger than 67108864 bytes": 64 MB for the disassembly or the decompiler of one function, 256 MB for every other view), or a file on the VM could not be read or written (a full disk: "a file could not be read or written on the VM: …", "the upload could not be stored: …"); 503 `{"error": "rizin not installed", "path"}`.

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/rizin/status` | `installed`, `path` (`TDC_RIZIN`), `version`, `ghidra` (rz-ghidra loads) |
| GET | `/api/rizin/files` | What the tab can open, existing non-empty files only: `submissions` (`filename`, `path`, `sha256`, `time`), `dumps` under `C:\dumps` (newest 500) and `uploads` (`name`, `path`, `size`) |
| POST | `/api/rizin/upload` | Upload a file (multipart `file`) to `%TEMP%\rizin_uploads` → `{"path"}` |
| POST | `/api/rizin/open` | Open a file. JSON: `path`, `tab` (browser tab ID) → `session`, `file` (`path`, the real one that was checked, `sha256`, `size`, `format`, `arch`, `bits`), `analysis`. A new file replaces the tab's session; the same file in another tab moves its session there, and while its session still closes it waits for that session's last save |
| GET | `/api/rizin/<sid>/status` | `analysis` (`state`, `step`, `done_steps`, `level`, `elapsed`, `note`), `seek`, `function`, without asking rizin |
| POST | `/api/rizin/<sid>/analyze` | Start the full analysis (aaa's steps one by one) → `analysis`. Between two steps the session pauses about 2 s, longer while requests use rizin (at most about 10 s), and answers requests; `step` is `null` then |
| POST | `/api/rizin/<sid>/close` | End the session (also the page's `sendBeacon` on pagehide) → `{"closed": true}` |
| GET | `/api/rizin/<sid>/functions` | `[{name, offset, size, nbbs}]` by address, read from rizin's `afl` (its row is about 63 B, while `aflj` carries about 2.7 KB per function); at most 200 000 of them, a line that is no row left out |
| GET | `/api/rizin/<sid>/disasm` | The function around `addr` from its start (the first page reaches `addr`), linear outside functions → `function`, `ops` (`offset`, `size`, `text`, `type`, `jump`, `comment`), `more` (outside functions not after a page of only invalid instructions; the RIZIN tab stops the linear disassembly after 2000 lines). Params: `addr`, `count` (default 400, at most 2000), `after` (the next page) |
| GET | `/api/rizin/<sid>/graph` | Basic blocks of the function around `addr` → `function`, `offset` (its entry), `nodes` (`offset`, `size`, `lines`, `jump`, `fail`, `cases`; edges only between its blocks) |
| GET | `/api/rizin/<sid>/decompile` | rz-ghidra's C for the function around `addr` → `available`, `reason`, `function`, `lines` (`text`, `offset` as `pdgo` shows it, `offsets`: every address of the line). `pdgj` may take up to 120 s (`DECOMPILE_TIMEOUT`); over it rizin is stopped and the session ends: 404 with `reason` "Decompiling took too long, the session ended." |
| GET | `/api/rizin/<sid>/hex` | Bytes at `addr` → `offset`, `bytes`, `paddr` (where they are in the opened file, from rizin's map there; `null` where no byte of the file is: a zero-filled part, no map, past the end). Param: `len` (default 512, at most 4096) |
| GET | `/api/rizin/<sid>/xrefs` | References to `addr` and from it; at a function's entry from the whole function → `scope`, `function`, `to`, `from` (`from`, `to`, `type`, `text`, `function`), `truncated` (over 500) |
| GET | `/api/rizin/<sid>/strings` | Strings, filtered and paged on the server → `total`, `items` (`offset`, `string`, `length`, `section`, `type`), `truncated` (rizin listed more than 200 000: the rest is left out). Params: `q`, `offset`, `limit` (default 200, at most 1000) |
| GET | `/api/rizin/<sid>/imports` | Imports, filtered (name or library) and paged → `total`, `items` (`offset`, `name`, `library`, `type`, `ordinal`), `truncated`. Params: `q`, `offset`, `limit` |
| GET | `/api/rizin/<sid>/flags` | Flag names for the console's Tab: those that start with `q` (any case), sorted → `total`, `names` (at most `limit`, default and most 200), `common` (the start all of them share, also those past `limit`), `truncated` (of more than 200 000 flags the rest is left out; of a `flj` over 32 MB none at all: `names` is empty and `common` is `""`, so Tab then lists the names of the tab's function list without completing one). rizin is asked again after a console command, a rename, a comment or an analysis step; requests that come while it is asked wait for that answer |
| POST | `/api/rizin/<sid>/seek` | JSON: `addr` (a number, `0x…`, or a function or flag name) → `seek`, `function` |
| POST | `/api/rizin/<sid>/console` | Run a rizin command. JSON: `cmd` → `output` (ANSI colours), `seek`, `function`, `truncated` (about 1 MB), `changed` (it renamed or commented). Allowlist on the server: no shell, no files, no other files opened, no writing to the file, no real debugging; writes into rizin's write cache, the breakpoint list and the `esil.*` and `io.cache` settings are open. A command that writes into the cache, sets a register or a setting, drives the emulation (`ae*`, `ar x=…`) or leaves a breakpoint other than the timeline began with is not recorded in the timeline of the emulation and **spoils** it: the timeline holds what the emulation routes did and nothing else (see GET `/patches`, `restore.reason`, and POST `/restore`) |
| POST | `/api/rizin/<sid>/rename` | Rename the function at `addr`. JSON: `addr`, `name` → `offset`, `name`; kept in the project |
| POST | `/api/rizin/<sid>/comment` | Comment at `addr` (an empty `text` removes it). JSON: `addr`, `text` → `offset`, `comment`; kept in the project |
| GET | `/api/rizin/<sid>/comment` | The comment at `addr` as the disassembly shows it → `offset`, `comment` (`""` without one); the right-click menu's Comment… field reads it where the disassembly has not loaded the address |
| POST | `/api/rizin/<sid>/emulation/start` | Start the emulation (ESIL) at `addr` (optional, default the current address). JSON: `addr` → the state as `GET …/emulation` answers it. Sets `io.cache=true` (without it the run's writes are lost; the file on disk is never written), `esil.timeout` (5 s: a run then stops by itself), the traps `esil.breakoninvalid`, `esil.exectrap`, `esil.iotrap`, `esil.nonull` (which stops **nothing** in rizin 0.9.1: measured, a read and a write at address 0 are carried out silently and the run goes on to the timeout, exactly as with `esil.nonull=false`; on a PE, where 0 is in no map, `esil.iotrap` is the guard that fires), `esil.verbose=1`, `esil.romem=false` and a 960 KB stack, then gives the ESIL memory of a run before back (see POST `…/emulation/stop`) and runs `aei`, `aeim`, `aepc`. The sweep comes first because rizin 0.9.1 maps a **second** stack at an address of its own once something has mapped memory beside the first one (measured), and the orphan would stay for the session. Registers other than the stack pointer, base pointer and PC keep the values they had (rizin's `aei` does not reset them). 400 `refused` when `io.cache` did not take or the stack could not be mapped. The first start of a session begins the timeline of the emulation, and every start is an action of it (see POST `/restore`) |
| GET | `/api/rizin/<sid>/emulation` | The emulation's state → `running`, `pc`, `registers` (`name`, `value`, as `ar` lists them), `changed` (the names that the last change of the registers changed), `stack` (up to 16 words from the stack pointer upwards, only those inside the stack the start mapped, and `[]` when the stack pointer is not in it: `addr`, `value`, `hint`: in a mapped region, the function the value is in (`name` or `name + offset`) or a flag exactly at it, never one of the emulator's register flags; otherwise `null`), `stopped` (why the run stopped, or `null`), `arch`, `bits`. **Every machine word travels as an exact `"0x…"` string** (lower case, no padding): `pc` (`null` where rizin names none), each register's `value` and each stack row's `addr` and `value`. A JSON number would reach the browser as a double, which cannot hold a 64-bit register (measured: `0x7ff7a1b2c3d4e5f6` arrived as `0x7ff7a1b2c3d4e400`), and the registers are editable there. The same holds for every answer that carries this state (start, run, register, POST `…/call`). **The breakpoint and patch routes answer addresses as integers**: those are bounded by the file's own layout, so the emulation routes answer in a different shape from them. 400 `refused` "the emulation is not started" before a start |
| POST | `/api/rizin/<sid>/emulation/stop` | Leave the emulation → `{"running": false}`. The write cache stays (it holds the patches), and the emulation's **memory is given back**: the file descriptor of every `mem.*` map of `omlj` is closed (`o- <fd>`), the assistant's buffers before the stack. Not with rizin's own `aeim-`: that gives back the region of the most recent `aeim` and can then name nothing at all ("cannot deinitialize mem.0x…"), so once the assistant has mapped a buffer the stack would stay mapped for good — measured, and with the buffers removed first by `om-`, by `o-` or not at all. `om-` would unmap without freeing (the `malloc://` descriptor stays open), `o-` does both. Only descriptors that no map outside `mem.*` uses are closed, so the sample's own is never touched; a descriptor whose map something removed without closing it would be in no map list any more and stay open until the session ends, but nothing can reach that state: the console refuses the whole `o` family, and every command the server sends that drops one of these maps closes it |
| POST | `/api/rizin/<sid>/emulation/run` | Run the emulation. JSON: `kind` (`step`, `over`, `skip`, `to_call`, `cont` or `until`; there is no step back: rizin 0.9.1's `aesb` restores no memory and the step after it runs without moving the PC), `addr` (for `until`) → the state, with `stopped`: why it stopped, one of `breakpoint` (rizin's `[ESIL] hit breakpoint`; also a disabled one: rizin 0.9.1 ignores `enabled`), `timeout` (`esil.timeout`, 5 s; read from the end of stderr, where a run that floods it with `int3` warnings says so), `invalid` (bytes rizin cannot decode), `trap` (the PC is where nothing can execute, or an invalid read or write) or `step` (it did what was asked). Before it runs, the start's `esil.*` settings are set again and `io.cache` and the stack are checked; 400 `refused` for an unknown `kind`, `until` without `addr`, a run before the start, `io.cache` that does not hold, an unmapped stack. `step` is `aes`; `over` is `aeso`, or `aesu` to the address after an indirect call, which `aeso` would step into; `skip` is `aess`, or the PC set after an indirect call (`call qword [import]`), which `aess` would run; `to_call` runs one step, then hops with `aesu` through the straight code to the next call of any kind (rizin's `aecc` runs past a call through the import table, and ignores `esil.timeout`) and stops before it; `cont` is `aec`; `until` is `aesu`. A run drops the cached strings, imports, flags and functions. Every run is an action of the timeline of the emulation (see POST `/restore`); a run that ends with `stopped: timeout` is on it all the same and **spoils** it, because its result hangs on the clock |
| POST | `/api/rizin/<sid>/emulation/register` | Set a register. JSON: `name` (one of those `ar` lists, otherwise 400 `refused`), `value` (decimal or `0x…`, as a string: a JSON number above 2^53 is not exact in a browser, so the state's `"0x…"` strings are what to send back) → the state. A register set by hand is not in the timeline of the emulation and **spoils** it (see POST `/restore`) |
| GET | `/api/rizin/<sid>/breakpoints` | The breakpoints rizin holds (`dblj`), lowest address first → `[{addr, enabled}]`. They are rizin's own, not the emulation's: they can be set before it starts, they survive it, and none of these three needs a running one. `enabled` is reported as rizin reports it, because a console `dbd` can set it — but rizin 0.9.1 stops a run at a disabled breakpoint all the same, so nothing here switches one off. The breakpoints are kept in the project: the same file opened again has them back (rizin's own project holds them, measured). A command or a condition that a project's breakpoint carries (`dbc`, `dbC`, which rizin runs when it hits) is taken off when the project loads, and a project whose breakpoints cannot be shown to be free of them is not used at all |
| POST | `/api/rizin/<sid>/breakpoints` | Set a breakpoint (`db @ addr`). JSON: `addr` → `breakpoints` (the list as GET answers it). Setting one that is there already leaves it as it is and is no error; 400 `refused` for an `addr` that is no address, for an `on` (there is none: remove the breakpoint instead) and when rizin left the address out of its list afterwards (another breakpoint covers it, on an arch whose breakpoints are wider than a byte). An address outside every map is set: rizin marks it `valid: false` and stops its runs there all the same. A breakpoint makes the session's project be written (a project now comes of a breakpoint alone). A set of breakpoints other than the one the timeline of the emulation began with spoils the timeline once an action follows, and keeps POST `/restore` refused until they are put back |
| DELETE | `/api/rizin/<sid>/breakpoints` | Remove the breakpoint at `addr` (`db- @ addr`), or all of them (`db-*`) for a request without one. JSON: `addr`, optional; an empty object or no body at all removes them all → `breakpoints`. Removing one that is not there is no error. The removal is saved too: the project is written again. Removing a breakpoint the timeline began with has the same effect on the timeline as setting another (see POST `/breakpoints`) |
| GET | `/api/rizin/<sid>/patches` | What rizin's write cache holds (`wcj`), lowest address first, and what waits → `{patches: [{addr, size, before, after, mine, over_run}], waiting: [{addr, after, reason, apply_now}], restore: {actions, reason, digests, refused}}`; `patches` has **one row per write operation, not per byte** (a two-byte `wx` is one row of `size` 2; a second write over the same address is another row whose `before` is what the first one wrote). `mine` is `true` for a write this session made through POST `/patch`, `false` for every other write in the cache — what an emulation run wrote, or a console `wx`, **also where that write lies inside a range this session patched**: rizin has one cache for both, so the session keeps a mirror of its own writes in the order it made them and matches it row by row against `wcj` (the cache is append-only and a removal keeps the order of the rest, both measured). `over_run` is `true` for a `mine` row that lies over bytes a foreign row written **before** it changed -- a patch set by hand into code an emulation run decrypted, which is what this tab invites. It matters because rizin's `before` for such a row is what the run wrote, which need not be what the file holds (measured: a file holding `73317331`, a run's `wx 41 @ 1` and then a patch `wx 90 @ 1` give a second row with `before: "41"` while the file still has `31`), so the pane marks the row and POST `/export` reads the file itself. It is `false` on every row that is not `mine`. A write of this session that no row holds any more (a console `wc-`, a restarted rizin) stops counting as its own. Two writes of the same bytes to the same address cannot be told apart; either of them is the same byte. rizin's `idx` and `written` are left out (the index changes with every removal, and nothing here ever commits the cache). The file on disk is never written. A console `e io.cache=false` leaves the rows listed but without effect: rizin then reads the file's bytes again. **What stays:** the rows with `mine: true` go into the project (its `/tdc` namespace, as `addr:hex`, or `addr:hex:r` for a row whose `over_run` is `true`) and are written back with `wx` when the file is opened again, before the first view loads; the rows with `mine: false` end with the session — they are bytes that never stood in the file. A saved patch whose address is in none of the new file's maps is left out, and the session's note says which. **`waiting` is what is held back:** a patch saved with the `:r` mark (it was set over bytes a run wrote) is **not** written when the file is opened — the open runs before any run, so it would land in the file's own, still encrypted bytes, and the next decryption would XOR over it instead of over the file's (measured on rizin 0.9.1: a patch `90` written first and the decryption run after leaves `6f`, neither the patch nor the decrypted `f9`). Each entry is `{addr, after, reason, apply_now}` (`addr` an integer, `after` the bytes as hex), lowest address first. **`apply_now` is a boolean and the pane's alone to draw "Apply now" from:** it is `true` where POST `/patch` with `waiting` would write the entry now -- a row of the cache that is not this session's own, a run's, overlaps a byte of it (`run_covers`; the order of the rows does not matter) -- and `false` everywhere else. It is made from the rows of the same read as the answer's `patches` (no second `wcj`), and it is only what is drawn: the press is decided again by the server on arrival, which refuses with its sentence where no run's bytes lie under the address by then. The `reason` also says, where no map of `omlj` holds the address **at that moment**, that none does and that an emulation maps memory of its own (its stack) when it starts — measured on rizin 0.9.1: `omlj` at the open lists the file's maps only and the `mem.*` map arrives with the emulation, so an unmapped address is not "never"; such a patch is held, not dropped. It stays in the project through every save, and the session's note says once, when the file is opened, which patches it held back. **A waiting patch is not in the cache and therefore not in `patches` and not exported**, and a patch the cache holds since (the same address and the same bytes made again) is no longer waiting — an entry is in one list of an answer, never both; the same address with other bytes leaves the saved entry waiting, because its own bytes are still not applied (POST `/export` takes the rows with `mine: true` from the cache). An entry saved without the mark comes from a project written before it and is applied as it always was. **`restore` is the offer of the restore button** (`RizinSession._restore_offered`), made from the same read of the cache as the rest of the answer -- one `wcj` for all of it. `{actions, reason, digests, refused}`: two questions with two fields. **`refused` is the button's:** `null` where POST `/restore` would run now, else the sentence it would refuse with (no timeline in the project, an emulation that runs -- also right after a restore, which leaves the replayed run going --, a cache that is not the one from opening, other breakpoints than the timeline ran under, a record without a range to prove). The pane enables the button on `refused: null` and says `refused` when it is not. **`reason` is the timeline's:** why the timeline would not be written to the project, which the pane's notice ("The way to this state is not kept in the project: …") says -- a register set by hand, a console write, a run that ended at the time limit, a breakpoint changed, a rizin that was restarted, something taken out of the cache, a run with nothing to prove -- and `null` where it can; it is the only field the taint reaches the pane by, and it does not decide the button. `actions` is how many actions the timeline has. **Read `digests` with what is asked, because it is not the same figure in the two cases.** For a session that has run a timeline of its own (its emulation has been started in this session, or its record was replayed) it is the number of ranges the cache proves **now**; for a session with none of its own that holds the project's timeline (a file just opened, or a rizin that was restarted) `actions` and `digests` are what the record **stores**, and its `reason` is `null`. A session with no timeline of either kind answers `{actions: 0, reason: <why its timeline is gone, or null>, digests: 0, refused}` and asks rizin for nothing more; with the project's timeline it also reads the breakpoints (`dblj`), which the answer does not cost otherwise. The same `restore` is in the answer of POST `/patch` and DELETE `/patch` with `waiting`, and in POST `/restore`'s `patches` |
| POST | `/api/rizin/<sid>/patch` | Write bytes at `addr` into the write cache (`wx … @ addr`) → `patches` (the list as GET answers it). JSON: `addr` plus **either** `bytes` (an even number of hex digits, at most **2000** bytes, nothing else: no spaces, no `0x`) **or** `kind`: `nop` (fill the instruction with `0x90`), `flip` (a conditional jump to its opposite), `always` (a conditional jump to an unconditional one to the same place: `eb` for `7x rel8`, `e9` for `0f 8x rel32`, whose displacement goes up by one because `e9` is a byte shorter, with a `nop` filling the length) or `nocall` (a call to `nop`s of its length). A `kind` reads the instruction with `pdj 1 @ addr` and needs no assembler (`wa` stays out: rizin can hand assembling to nasm or as); it is x86 only. Needs no running emulation: `io.cache=true` is set and read back first, because without it rizin loses the write and says so on stderr only. 400 `refused` for a bad `addr`, for `bytes` and `kind` together or neither, for bytes that are no even-length hex or longer than 2000, for a `kind` that does not apply to the instruction there (`'call' is no x86 conditional jump …`), for an address where rizin decoded no instruction, on another arch, when `io.cache` did not take, and when rizin's cache holds no write at the address afterwards. **Why 2000 bytes:** a patch is one write, so it is one `wcj` row — and taking one back sends `wc- <addr> <addr+1>`, which removes a row, so a patch is never split over several commands. Its size is therefore what one command line can carry: rizin 0.9.1 reads its stdin a line at a time and keeps **4094** characters of it, runs what is left as it stands, and says nothing at all about the cut — so the write lands at whatever address survives it (measured, a `wx` at `0x50004000`: 4094 characters wrote 2039 bytes where they were asked to, 4095 wrote them at `0x5000400` and 4096 at `0x500040`; the bytes asked for are nowhere, and the row in the cache is at an address nobody named). `wx <2 × 2000 hex> @ 0x<16 digits>` is 4024 characters, well inside it. Drops the cached strings, imports, flags and functions, and makes the project be written (a patch alone is reason enough for one). At most 32 KB of `addr:hex` fit into the project; what does not fit is left out of the save and the session's note says how many, so the analysis progress in the same namespace is never at risk. **`{addr, waiting: true}` writes the patches that wait at `addr` (see GET `/patches`) now, instead of `bytes` or `kind`:** one of the two ways out of waiting, and the server decides when it is offered, not the pane. It is written only where the bytes under the address are a run's again, i.e. a row of the cache that is not this session's own covers it (`run_covers`); a patch written before that is the harm that held it back (the next decryption would XOR over it). Answers `patches`, `waiting` and `restore` as GET `/patches` does; 400 `refused` where no patch waits at `addr`, where no run's bytes cover it, when `waiting` comes with `bytes` or `kind`, and when `waiting` is not `true` or `false`. It is a patch like any other afterwards (it is written into the cache, recorded in the session's timeline if it has one, and saved). |
| DELETE | `/api/rizin/<sid>/patch` | Take back **every write that overlaps `addr`** (`wc- addr addr+1`: an explicit range, because `wc- addr` alone drops every write in a whole block of 0x100 bytes from there). rizin removes a write operation whole, so taking back one byte of a 2000-byte `wx` takes all 2000, and both writes at an address a second `wx` covered go together; the `patches` answered afterwards shows what is left. Without an `addr`, the whole cache (`wc-*`) — **an emulation run's bytes included**, since rizin has one. JSON: `addr`, optional; an empty object or no body at all takes them all back → `patches` and `run_removed`. **`run_removed`** is the writes that were **not** patches of this session and went all the same, each as `{addr, size}`, lowest first: taking back a patch set over bytes an emulation run wrote drops the run's whole row with it -- up to a copied or decrypted stage (measured: a 4-byte run row and a 1-byte patch over it, and `wc- 0x1 0x2` left the cache empty). Those bytes are back only by running again, so the answer names them and the pane says so. Taking back where there is nothing is no error; 400 `refused` for a bad `addr` and when rizin kept the write. Saved as well: a patch taken back does not come back at the next open. **Nor does the project's timeline of the emulation outlive it where it makes that patch:** a replay would write the patch again and say it restored the bytes -- the SHA-256 cannot tell, the patch lies outside the hashed ranges -- so taking back a patch that the saved timeline holds an action for drops the timeline (it is not in the next save, and POST `/restore` refuses with the reason); a patch the timeline does not make (one made before the emulation was first started) costs it nothing. **The console's `wc-` and `wc-*` do the same:** the session's mirror of its own writes notices a patch that left the cache wherever it left by, at the next read of the cache (this route's, GET `/patches`'s, a save's), and drops the timeline then, which asks for a save. Starting the emulation again does *not* clear a run's writes (it would take the hand-made patches with it, which are meant to stick), so they outlive a restart: the cache sits above the stack `aeim` maps, and a restarted run's stack still shows the words the last one wrote there — this is the way to clear them. **A patch that waits (see GET `/patches`) is not taken back by this:** it is no write of rizin's cache, so neither `wc-*` nor an address can reach it, and it stays in the project and in `waiting` — it leaves with `{addr, waiting: true}` below, not through the forms above. **`{addr, waiting: true}` takes the patches that wait at `addr` out of the list and out of the project:** the other way out of waiting, and the only one that discards what the project holds. `addr` is required (400 `refused` without it, and where no patch waits there); a patch of the same bytes that a restarted rizin lost goes with it, and the project's timeline of the emulation goes too when it makes that patch again -- replaying it would put back what was taken out. Answers `patches`, `waiting` and `restore` as GET `/patches` does; the cache is not touched. Drops the cached views like POST `/patch` |
