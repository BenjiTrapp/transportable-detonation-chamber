# API Reference

Which routes the Web UI serves on port 9000, and which tools the MCP server
offers to an MCP client.

Responses are JSON.

## Named Pipe Interception

| Method | Endpoint | Description |
|--------|----------|-------------|
| GET | `/api/pipes/intercept` | Interception sessions (live and ended), newest first |
| POST | `/api/pipes/intercept` | Start a session → 201 session (state `starting` until the first upstream is open, then `active`; `armed` while an arm session waits) / 400 error. JSON: `pattern` (required), `mode` (`observe`/`hold`), `how` (`attach`/`arm`), `match` (`exact`/`prefix`/`regex`), `squat` (arm + exact only), `max_duration` (default 600 s, at most 3600), `hold_timeout` (default 30 s, at most `max_duration`; both finite), `pipe_mode` (`byte`/`message`; skips probing the real server). Refused (400): `\lsass`, `\ntsvcs`, `\protected_storage`, `\lsarpc`, `\samr`, `\netlogon`, `\svcctl`, `\epmapper`, `\InitShutdown`; arm + exact for a pipe that already exists. 429 with 16 live sessions; 413 for a body over 2 MiB |
| GET | `/api/pipes/intercept/<sid>` | One session (state, target, connection and message counts, `self_connect_retries`: upstream connects that landed on the proxy's own instance and were retried) |
| DELETE | `/api/pipes/intercept/<sid>` | End a session; held messages are forwarded, both ends are closed |
| GET | `/api/pipes/intercept/<sid>/messages` | Recorded messages (`seq`, `conn`, `dir` `c2s`/`s2c`, `data_b64`, `state`: `held`, `passed`, `auto_passed`, `edited`, `dropped`, or `write_failed` when relaying a decided message failed). Params: `after` (seq), `limit` (default 200, max 1000) |
| POST | `/api/pipes/intercept/<sid>/messages/<seq>` | Decide a held message. JSON: `action` (`forward`/`drop`/`edit`), `data_b64` (for `edit`) |
| POST | `/api/pipes/intercept/<sid>/release` | Forward every held message → `{"released": n}` |
| GET | `/api/pipes/intercept/<sid>/export` | Session and all messages as a JSON attachment |

Windows hands a connecting client the oldest free instance of a pipe, whoever owns it. Once a session is `active` the proxy keeps that a proxy instance: when a client arrives it first creates its next listening instance and only then connects upstream for this client, so the connect takes the real server's current spare and the server's next spare is younger than the proxy's. Only before the first client is an upstream opened in advance (that is what the `starting` state waits for); it consumes the server instance that predates the session, and right after the first client one more upstream is opened and closed at once to consume the spare the server created for it. After that the server never holds an idle proxy connection. If an upstream connect lands on the proxy's own instance instead (the instance's client process id is the web UI's), the proxy closes it, gives the server a moment to create its next instance (backing off up to 1 s) and retries with a fresh instance; each such episode counts once in `self_connect_retries`. Without `pipe_mode`, the proxy reads the real server's pipe mode from a throw-away instance of its own (Windows gives every instance the type of the first one), so the probe never takes one of the server's instances; passing `pipe_mode` skips it. Only one live session may own a pipe: a second session for the same exact name is refused (400), and armed prefix/regex watchers skip pipes another session owns, because one session's upstream connect could otherwise land on the other's listening instance. Not intercepted are connections that existed before the session started or were made while it was `starting`, and a client that connects in the instant in which no proxy instance is listening (during a self-connect retry, or while the real server had no free instance).

## Rizin

One rizin session per opened file and browser tab (RIZIN tab). Addresses are integers in answers, except the machine words of the emulation routes (`pc`, the registers, the stack, the assistant's offered `value`), which are exact `"0x…"` strings (see the emulation rows); in requests `addr` is decimal or `0x…`. Errors: 400 `{"refused": reason}` for invalid input, a refused console command or a file that cannot be opened (missing, empty, a folder); 403 for a UNC path or a path outside the folders that `/api/file/download` serves too (which include the uploads in `%TEMP%\rizin_uploads`); 404 `{"error": "session ended"}` (with `reason` when rizin stopped during that request); 409 `{"busy": true, "step"}` while an analysis step or another request has rizin (views wait about 2 s first), `{"moved": true}` once the file was opened in another tab, or `{"superseded": true}` for an open that a newer open of the same tab overtook; 500 `{"error"}` when rizin could not open the file ("rizin could not open the file: …"), answered something unexpected ("rizin answered something unexpected: …") or answered one of the three lists that are filtered on the server (strings, imports, flag names) with more than 32 MB ("too many strings to list here …: filter them in the console") or answered more than the limit of the command it ran ("rizin's answer to pdfj is larger than 67108864 bytes": 64 MB for the disassembly or the decompiler of one function, 256 MB for every other view), or a file on the VM could not be read or written (a full disk: "a file could not be read or written on the VM: …", "the upload could not be stored: …"); 503 `{"error": "rizin not installed", "path"}`.

| POST | `/api/rizin/<sid>/emulation/start` | Start the emulation (ESIL) at `addr` (optional, default the current address). JSON: `addr` → the state as `GET …/emulation` answers it. Sets `io.cache=true` (without it the run's writes are lost; the file on disk is never written), `esil.timeout` (5 s: a run then stops by itself), the traps `esil.breakoninvalid`, `esil.exectrap`, `esil.iotrap`, `esil.nonull` (which stops **nothing** in rizin 0.9.1: measured, a read and a write at address 0 are carried out silently and the run goes on to the timeout, exactly as with `esil.nonull=false`; on a PE, where 0 is in no map, `esil.iotrap` is the guard that fires), `esil.verbose=1`, `esil.romem=false` and a 960 KB stack, then gives the ESIL memory of a run before back (see POST `…/emulation/stop`) and runs `aei`, `aeim`, `aepc`. The sweep comes first because rizin 0.9.1 maps a **second** stack at an address of its own once something has mapped memory beside the first one (measured), and the orphan would stay for the session. Registers other than the stack pointer, base pointer and PC keep the values they had (rizin's `aei` does not reset them). 400 `refused` when `io.cache` did not take or the stack could not be mapped. The first start of a session begins the timeline of the emulation, and every start is an action of it (see POST `/restore`) |
| GET | `/api/rizin/<sid>/emulation` | The emulation's state → `running`, `pc`, `registers` (`name`, `value`, as `ar` lists them), `changed` (the names that the last change of the registers changed), `stack` (up to 16 words from the stack pointer upwards, only those inside the stack the start mapped, and `[]` when the stack pointer is not in it: `addr`, `value`, `hint`: in a mapped region, the function the value is in (`name` or `name + offset`) or a flag exactly at it, never one of the emulator's register flags; otherwise `null`), `stopped` (why the run stopped, or `null`), `arch`, `bits`. **Every machine word travels as an exact `"0x…"` string** (lower case, no padding): `pc` (`null` where rizin names none), each register's `value` and each stack row's `addr` and `value`. A JSON number would reach the browser as a double, which cannot hold a 64-bit register (measured: `0x7ff7a1b2c3d4e5f6` arrived as `0x7ff7a1b2c3d4e400`), and the registers are editable there. The same holds for every answer that carries this state (start, run, register, POST `…/call`). **The breakpoint and patch routes answer addresses as integers**: those are bounded by the file's own layout, so the emulation routes answer in a different shape from them. 400 `refused` "the emulation is not started" before a start |
| POST | `/api/rizin/<sid>/emulation/stop` | Leave the emulation → `{"running": false}`. The write cache stays (it holds the patches), and the emulation's **memory is given back**: the file descriptor of every `mem.*` map of `omlj` is closed (`o- <fd>`), the assistant's buffers before the stack. Not with rizin's own `aeim-`: that gives back the region of the most recent `aeim` and can then name nothing at all ("cannot deinitialize mem.0x…"), so once the assistant has mapped a buffer the stack would stay mapped for good — measured, and with the buffers removed first by `om-`, by `o-` or not at all. `om-` would unmap without freeing (the `malloc://` descriptor stays open), `o-` does both. Only descriptors that no map outside `mem.*` uses are closed, so the sample's own is never touched; a descriptor whose map something removed without closing it would be in no map list any more and stay open until the session ends, but nothing can reach that state: the console refuses the whole `o` family, and every command the server sends that drops one of these maps closes it |
| POST | `/api/rizin/<sid>/emulation/run` | Run the emulation. JSON: `kind` (`step`, `over`, `skip`, `to_call`, `cont` or `until`; there is no step back: rizin 0.9.1's `aesb` restores no memory and the step after it runs without moving the PC), `addr` (for `until`) → the state, with `stopped`: why it stopped, one of `breakpoint` (rizin's `[ESIL] hit breakpoint`; also a disabled one: rizin 0.9.1 ignores `enabled`), `timeout` (`esil.timeout`, 5 s; read from the end of stderr, where a run that floods it with `int3` warnings says so), `invalid` (bytes rizin cannot decode), `trap` (the PC is where nothing can execute, or an invalid read or write) or `step` (it did what was asked). Before it runs, the start's `esil.*` settings are set again and `io.cache` and the stack are checked; 400 `refused` for an unknown `kind`, `until` without `addr`, a run before the start, `io.cache` that does not hold, an unmapped stack. `step` is `aes`; `over` is `aeso`, or `aesu` to the address after an indirect call, which `aeso` would step into; `skip` is `aess`, or the PC set after an indirect call (`call qword [import]`), which `aess` would run; `to_call` runs one step, then hops with `aesu` through the straight code to the next call of any kind (rizin's `aecc` runs past a call through the import table, and ignores `esil.timeout`) and stops before it; `cont` is `aec`; `until` is `aesu`. A run drops the cached strings, imports, flags and functions. Every run is an action of the timeline of the emulation (see POST `/restore`); a run that ends with `stopped: timeout` is on it all the same and **spoils** it, because its result hangs on the clock |
| POST | `/api/rizin/<sid>/emulation/register` | Set a register. JSON: `name` (one of those `ar` lists, otherwise 400 `refused`), `value` (decimal or `0x…`, as a string: a JSON number above 2^53 is not exact in a browser, so the state's `"0x…"` strings are what to send back) → the state. A register set by hand is not in the timeline of the emulation and **spoils** it (see POST `/restore`) |
| GET | `/api/rizin/<sid>/breakpoints` | The breakpoints rizin holds (`dblj`), lowest address first → `[{addr, enabled}]`. They are rizin's own, not the emulation's: they can be set before it starts, they survive it, and none of these three needs a running one. `enabled` is reported as rizin reports it, because a console `dbd` can set it — but rizin 0.9.1 stops a run at a disabled breakpoint all the same, so nothing here switches one off. The breakpoints are kept in the project: the same file opened again has them back (rizin's own project holds them, measured). A command or a condition that a project's breakpoint carries (`dbc`, `dbC`, which rizin runs when it hits) is taken off when the project loads, and a project whose breakpoints cannot be shown to be free of them is not used at all |
| POST | `/api/rizin/<sid>/breakpoints` | Set a breakpoint (`db @ addr`). JSON: `addr` → `breakpoints` (the list as GET answers it). Setting one that is there already leaves it as it is and is no error; 400 `refused` for an `addr` that is no address, for an `on` (there is none: remove the breakpoint instead) and when rizin left the address out of its list afterwards (another breakpoint covers it, on an arch whose breakpoints are wider than a byte). An address outside every map is set: rizin marks it `valid: false` and stops its runs there all the same. A breakpoint makes the session's project be written (a project now comes of a breakpoint alone). A set of breakpoints other than the one the timeline of the emulation began with spoils the timeline once an action follows, and keeps POST `/restore` refused until they are put back |
| DELETE | `/api/rizin/<sid>/breakpoints` | Remove the breakpoint at `addr` (`db- @ addr`), or all of them (`db-*`) for a request without one. JSON: `addr`, optional; an empty object or no body at all removes them all → `breakpoints`. Removing one that is not there is no error. The removal is saved too: the project is written again. Removing a breakpoint the timeline began with has the same effect on the timeline as setting another (see POST `/breakpoints`) |
| GET | `/api/rizin/<sid>/patches` | What rizin's write cache holds (`wcj`), lowest address first, and what waits → `{patches: [{addr, size, before, after, mine, over_run}], waiting: [{addr, after, reason, apply_now}], restore: {actions, reason, digests, refused}}`; `patches` has **one row per write operation, not per byte** (a two-byte `wx` is one row of `size` 2; a second write over the same address is another row whose `before` is what the first one wrote). `mine` is `true` for a write this session made through POST `/patch`, `false` for every other write in the cache — what an emulation run wrote, or a console `wx`, **also where that write lies inside a range this session patched**: rizin has one cache for both, so the session keeps a mirror of its own writes in the order it made them and matches it row by row against `wcj` (the cache is append-only and a removal keeps the order of the rest, both measured). `over_run` is `true` for a `mine` row that lies over bytes a foreign row written **before** it changed -- a patch set by hand into code an emulation run decrypted, which is what this tab invites. It matters because rizin's `before` for such a row is what the run wrote and **not** what the file holds (measured: a file holding `73317331`, a run's `wx 41 @ 1` and then a patch `wx 90 @ 1` give a second row with `before: "41"` while the file still has `31`), so the pane marks the row and POST `/export` reads the file itself. It is `false` on every row that is not `mine`. A write of this session that no row holds any more (a console `wc-`, a restarted rizin) stops counting as its own. Two writes of the same bytes to the same address cannot be told apart; either of them is the same byte. rizin's `idx` and `written` are left out (the index changes with every removal, and nothing here ever commits the cache). The file on disk is never written. A console `e io.cache=false` leaves the rows listed but without effect: rizin then reads the file's bytes again. **What stays:** the rows with `mine: true` go into the project (its `/tdc` namespace, as `addr:hex`, or `addr:hex:r` for a row whose `over_run` is `true`) and are written back with `wx` when the file is opened again, before the first view loads; the rows with `mine: false` end with the session — they are bytes that never stood in the file. A saved patch whose address is in none of the new file's maps is left out, and the session's note says which. **`waiting` is what is held back:** a patch saved with the `:r` mark (it was set over bytes a run wrote) is **not** written when the file is opened — the open runs before any run, so it would land in the file's own, still encrypted bytes, and the next decryption would XOR over it instead of over the file's (measured on rizin 0.9.1: a patch `90` written first and the decryption run after leaves `6f`, neither the patch nor the decrypted `f9`). Each entry is `{addr, after, reason, apply_now}` (`addr` an integer, `after` the bytes as hex), lowest address first. **`apply_now` is a boolean and the pane's alone to draw "Apply now" from:** it is `true` where POST `/patch` with `waiting` would write the entry now -- a row of the cache that is not this session's own, a run's, overlaps a byte of it (`run_covers`; the order of the rows does not matter) -- and `false` everywhere else. It is made from the rows of the same read as the answer's `patches` (no second `wcj`), and it is only what is drawn: the press is decided again by the server on arrival, which refuses with its sentence where no run's bytes lie under the address by then. The `reason` also says, where no map of `omlj` holds the address **at that moment**, that none does and that an emulation maps memory of its own (its stack) when it starts — measured on rizin 0.9.1: `omlj` at the open lists the file's maps only and the `mem.*` map arrives with the emulation, so an unmapped address is not "never"; such a patch is held, not dropped. It stays in the project through every save, and the session's note says once, when the file is opened, which patches it held back. **A waiting patch is not in the cache and therefore not in `patches` and not exported**, and a patch the cache holds since (the same address and the same bytes made again) is no longer waiting — an entry is in one list of an answer, never both; the same address with other bytes leaves the saved entry waiting, because its own bytes are still not applied (POST `/export` takes the rows with `mine: true` from the cache). An entry saved without the mark comes from a project written before it and is applied as it always was. **`restore` is the offer of the restore button** (`RizinSession._restore_offered`), made from the same read of the cache as the rest of the answer -- one `wcj` for all of it. `{actions, reason, digests, refused}`: two questions with two fields. **`refused` is the button's:** `null` where POST `/restore` would run now, else the sentence it would refuse with (no timeline in the project, an emulation that runs -- also right after a restore, which leaves the replayed run going --, a cache that is not the one from opening, other breakpoints than the timeline ran under, a record without a range to prove). ## Dashboards

Own dashboards of the Dashboard tab: a tile is a saved log search. Nothing is computed
on the server — the browser fetches every tile's numbers from `/api/logs/search`. Kept in

## Firewall

Times are ISO-8601 UTC text; a flow's `times` is a list of epoch seconds. Errors are `{"error": ...}` with 400 (malformed), 404, 409 (refused: the Windows Firewall is off, a lockout, a block that could not be verified) or 500. Every action is an `access` event in the LOGS tab — the ones TDC takes by itself under `/internal/firewall/block`, `/internal/firewall/decide` and `/internal/firewall/fetch`, each with `by` (`detector`, `analyst` or `deadline`), the endpoint, the URL, the User-Agent that was sent and the outcome.

ISOLATED blocks the default way out and switches off Windows' own outbound Allow rules; what still gets out is in `allowed_out`. TDC's own fetch is let out one address at a time, only while it runs (`TDC-FW-ISO-fetch-*`, one rule per binary the fetch can run as, removed when the fetch ends, retried at every collector round, and swept at start-up and once a minute for a rule a crash left behind); what that leaves open is in `residual` of `GET /api/firewall/isolate`. A rule that could not be removed again is named in `fetch_paths_open` there, on the capture (`allow_closed`: `true` gone, `false` still standing with `close_problem` saying why, `null` nothing to close because ISOLATED is off, or because ISOLATED is on but the fetch gave up waiting for a sweep (or for the removal of that endpoint's rules) and opened none, with `allow_problem` saying so) and as an `/internal/firewall/allow` event in LOGS.

|--------|----------|-------------|
| GET | `/api/firewall/connections` | Bundled flows with `tags`, `severity`, `geo` (`scope`, `cc`, `country`, `lat`, `lon`, `asn`, `as_org`), `state` (`allowed`, `blocked`, `pending`), `rule_id`, `capture_ids`. Params: `since`, `until` (ISO-8601 or epoch), `process` (substring of the image), `tag`, `state`, `max` (1-5000, default 500). Also `count`, `truncated`, `rules_error` (why the rules could not be read; nothing is then claimed as blocked), `isolated`, `ask_mode`, `sources` |
| GET | `/api/firewall/summary` | Totals, blocked and pending flows, top processes, endpoints and countries of the same window, plus `open_decisions`, `captures_total`, `geo_available` |
| GET | `/api/firewall/geo` | One offline lookup: `ip` gives `{ip, geo, available}` |
| GET | `/api/firewall/rules` | The `TDC-FW-*` rules that stand, one entry per rule: `rule_id`, `kind`, `image`, `ip`, `port`, `protocol`, `key`, `blocking`, `cuts` (true only for `TDC-FW-ISO-cut` standing as the catch-all Block) |
| POST | `/api/firewall/block` | `{scope, image, ip, port, protocol}`. `endpoint`: this program to `ip`; `endpoint_all`: every program, TDC's fetcher included; `process`: `image` anywhere. 409 while a firewall profile is off |

The PowerShell reads behind it are cached: `profiles_off` for 60 s, but for 10 s while ISOLATED is on or after an error; `allowed_out` for 10 s; in the cut stages the read of the cut rule for 10 s (the rule list the tab polls counts as one). `profiles_off` and `allowed_out` are read again after every enforcement route. ## MCP Server

`mcp/server.py` exposes the lab to MCP clients (Claude Code, Claude Desktop, ...)
over stdio (49 tools). It talks to the web UI API, so the VM must be reachable.

```bash
make mcp-setup        # creates mcp/.venv (Python >= 3.10) from mcp/requirements.txt
```

`.mcp.json` in the repository root registers it for Claude Code; set `TDC_URL`
there if the VM is not at `http://192.168.64.4:9000`.

Every request of the MCP server carries `X-TDC-Client: mcp` and
`X-TDC-MCP-Tool: <tool name>`; the web UI logs them as `mcp` events, so a search
such as `source=mcp | stats count by tool` shows what an MCP client did.

Not exposed on purpose: byte patching (`/api/file/hex/write`), clearing the
scan history, starting, stopping or steering pipe interception (forward, drop,
edit), the raw service proxies, and everything of the FIREWALL tab that acts
(block, unblock, ISOLATED, the ASK switch, answering a decision, KILL, turning
the firewall on): a model must not take the chamber off the network or lift a
block on its own.
