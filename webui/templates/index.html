Transportable Detonation Chamber

v1.0 — Malware Analysis & EDR Testing Platform

What is Detonation Chamber?

A pre-configured Windows 11 VM for detonating samples and watching them with several EDR-style engines at once. This web UI combines their telemetry with live-memory forensics into one verdict per detonation.

Key Capabilities

🔍
Real-time Detection
Sigma, YARA and IOC matching via Rustinel; kernel ETW behavior rules via Fibratus; Sysmon events
🧠
Live Memory
Aether, Process Dump, Hunt-Sleeping-Beacons, BeaconEye and an exit-time dump, scored by one evidence model with a host baseline
🛡
Static Scanning
ThreatCheck, DefenderCheck, EMBER2024 (ML), capa (ATT&CK capabilities), LitterBox
📊
Binary Analysis
PE/ELF parsing, packer detection, entropy, file map, hex editor

Workflow

  1. Submit a sample (Submit tab, make submit or the MCP tool tdc_submit_file)
  2. DetonatorAgent runs it; exit capture is armed first
  3. Rustinel, Fibratus, Sysmon record what it does
  4. Live-memory scanners examine the running process (1–2 minutes); if it exits, its exit dump is analyzed instead
  5. Read the verdict in Submit, then follow up in Tracing, Graph and Sysmon

Process instances

Windows reuses PIDs. The UI tracks every process instance separately: 1234 is the newest process with PID 1234, 1234@1789372861 an earlier one. Alerts, events and children belong to the instance that was running at the time.

Tab Guide

Dashboard

Stats strip (alerts, processes, services, rules, tools), one card per service with launch buttons, recent activity.

Tracing

Per-process console: verdict, timeline by event type, process tree and alert table. Click an alert for its full raw event and Sigma match details.

Graph

Process tree around a process. Layouts: process tree, force-directed, isometric (foldable subtrees, activity icons, remote threads as bridges). The landing page lists samples and candidate processes; click a node for its detail panel.

Sysmon

Sysmon events with search, type and PID filters, and the Windows Event IDs each event corresponds to.

ThreatScan

ThreatCheck, DefenderCheck, EMBER2024 and capa on a file. The Live Process Memory panel scans a running PID with Aether, dumps it with Process Dump, captures the host baseline or sweeps every process.

ETW

Event Log browser across 12 channels with live threat highlighting; click an event to see all fields.

Hex

Hex editor with data inspector and structure minimap. PE/ELF Analysis parses headers, sections, imports and IOC flags; Inspect shows a section's hex dump and strings.

FileMap

Byteplot, entropy and PE/ELF structure planes side by side with import/export trees; click to jump to an offset.

LitterBox

Files in the LitterBox sandbox with static, dynamic and EDR results.

Submit

Detonate a sample and follow its stages. The verdict combines EDR alerts, live memory (Aether, Process Dump, beacon scanners), the exit-time dump, network beaconing and LitterBox.

API

Served on port 9000, JSON. No login (keep the VM on an isolated network); state-changing requests from other web sites are refused. The full reference with all endpoints is in the README; the MCP server (mcp/server.py, 41 tools) wraps the same API.

Architecture

Web UI :9000 ──submit──▶ DetonatorAgent :8080 ──runs──▶ sample
     │    └────────────▶ LitterBox :1337 (static + dynamic)
     │
     ├──◀── alerts ── Rustinel (Sigma/YARA/IOC) · Fibratus (ETW) · Sysmon
     │
     └──── live memory ──▶ Aether · Process Dump · HSB · BeaconEye
                          Exit Capture (dump at process exit)

Data Flow

  1. Sample submitted → DetonatorAgent and/or LitterBox; exit capture armed for its image name
  2. DetonatorAgent executes it and returns the PID
  3. Rustinel, Fibratus and Sysmon record its activity
  4. Hunt-Sleeping-Beacons, BeaconEye, Aether (3 samples) and Process Dump scan the PID
  5. Sysmon network events are checked for periodic connections
  6. All memory findings are scored together (persistence, corroboration, host baseline) and combined with EDR alerts and LitterBox into one verdict

Detection Rules

Sigma
rustinel-rules windows-advanced pack: process creation, registry persistence, tasks, services, script blocks
YARA
rustinel-rules + Elastic protections-artifacts; loaded counts are shown on the Dashboard
IOC
SHA-256, IP, domain and path matching; sample hashes are added on submission
In-memory signatures
Aether's rule files (C2 strings, reflective loading, beacon fields), mapped to ATT&CK

On ARM64 VMs

  • Aether, Hunt-Sleeping-Beacons and BeaconEye run as x64 builds under emulation; they see x64 processes reliably — which samples on ARM64 are
  • Results for native ARM64 processes are marked as limited and count only half
  • Exit dumps of emulated processes: the emulator's own executable memory is recognized and not scored
