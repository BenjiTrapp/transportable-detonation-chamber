Transportable Detonation Chamber

v1.0 — Malware Analysis & EDR Testing Platform

What is Detonation Chamber?

A pre-configured Windows 11 VM for detonating samples and watching them with several EDR-style engines at once. This web UI combines their telemetry with live-memory forensics into one verdict per detonation.

Key Capabilities

🔍
Real-time Detection
Sigma, YARA and IOC matching via Rustinel; kernel ETW behavior rules via Fibratus; Sysmon events
🧠
Live Memory
Aether, Process Dump, Hunt-Sleeping-Beacons, BeaconEye and an exit-time dump, scored by one evidence model with a host baseline
🛡
Static Scanning
ThreatCheck, DefenderCheck, EMBER2024 (ML), capa (ATT&CK capabilities), LitterBox
📊
Binary Analysis
PE/ELF parsing, packer detection, entropy, file map, hex editor

Workflow

  1. Submit a sample (Submit tab, make submit or the MCP tool tdc_submit_file)
  2. DetonatorAgent runs it; exit capture is armed first
  3. Rustinel, Fibratus, Sysmon record what it does
  4. Live-memory scanners examine the running process (1–2 minutes); if it exits, its exit dump is analyzed instead
  5. Read the verdict in Submit, then follow up in Tracing, Graph and Sysmon

Process instances

Windows reuses PIDs. The UI tracks every process instance separately: 1234 is the newest process with PID 1234, 1234@1789372861 an earlier one. Alerts, events and children belong to the instance that was running at the time.

Themes and card controls

✶ switches between the Classic and the Cyberpunk theme at once, without reloading the page: the open tab, an open detail view, filters and drilldown steps, the graph and running interception sessions stay as they are. This browser remembers the choice; without one the UI starts in Cyberpunk, the default. In Classic ✶ sits below "? Help". In Cyberpunk it is at the right end of the top bar, where ☰ PROCESSES opens the process list and the timeline, "…" holds the tabs that do not fit and "n/m ONLINE" lists the five services of the status row (Rustinel, Sysmon, Fibratus, Agent, LitterBox); the SERVICES ONLINE tile also counts the Detonator.

In both themes (i) beside a title explains its card, CHART / TABLE shows the numbers of a chart as a table, a click on a column head sorts the table (a second click reverses the order), and a dashboard tile opens what it counts.

Charts

The charts of the Dashboard, Alerts, Sysmon, ThreatScan and Submit tabs, of a graph node's detail and of the detonation results take the colours of the theme, and CHART / TABLE lists their numbers. A click on a bar, a slice, a legend row or a Sankey node of the Dashboard, Alerts and Sysmon charts filters by it (the dashboard opens the Alerts tab with that filter): a time range, category, rule, process, image or event type set this way shows as a chip in the filter bar, and its × takes it off. On the dashboard, 24H / 7D / 30D / ALL choose the range (ALL by default) and a drag across the bars narrows the donuts to the range drawn. In the Alerts tab a drag across the bars of OVER TIME narrows the whole tab to the bars it covers, and each click or range there that changes a filter is a step of the drilldown bar above the charts: ‹ BACK takes the last step back, a step of its path (ALL ALERTS › …) jumps back to it. Sankeys are drawn by square roots so small flows stay visible; LINEAR shows true proportions.

Tab Guide

Dashboard

Stats strip (alerts, processes, services, rules, tools; TOTAL ALERTS and PROCESSES TRACKED with 45-day sparklines), ALERT ACTIVITY (alerts stacked by severity) with the SEVERITY and CATEGORY donuts of its range, one card per service with launch buttons, recent activity. A tile opens what it counts (the high / med / low counts of TOTAL ALERTS open the Alerts tab filtered by severity); a bar or a segment opens the Alerts tab filtered to it, and a drag across the bars narrows the donuts to the range drawn.

Alerts

Every alert in one table, newest first, under charts of the alerts the filters let through: SEVERITY, OVER TIME, ENGINE and the Sankey FLOW: ENGINE → RULE → PROCESS. Filter by severity (several at once), engine and text (rule, process, description), or click a chart (here or on the dashboard): a time range, category, rule or process becomes a chip in the filter bar whose × takes it off. Drag across the bars of OVER TIME to narrow the tab to the bars the dashed box covers; the bars then divide that range anew, down to seconds for a short one. Each click on a chart and each range drawn that changes a filter is a step in the drilldown bar above the charts: ‹ BACK takes the last step back, a step of the path (ALL ALERTS › 27 Jul › 27 Jul 10:00–12:00) jumps back to it, ALL ALERTS takes every step back. What you set in the filter bar yourself (severity chips, engine, search, the × of a chip) is no step, and BACK leaves it alone; a jump from the dashboard starts a new path. The steps last until the page is reloaded. "n of m" counts the matches, and the newest 2000 of them are listed; the tab scrolls as a whole, the drilldown bar and the filter bar stay at its top. Click a row for the alert's details, a process name for its process (only processes in the process list are links).

Tracing

Per-process console: verdict, timeline by event type, process tree and alert table. Click an alert for its full raw event and Sigma match details.

Graph

Process tree around a process. Layouts: process tree, force-directed, isometric (foldable subtrees, activity icons, remote threads as bridges). The landing page lists samples and candidate processes; click a node for its detail panel, where ACTIVITY MIX shows its Sysmon activity by kind.

Pipes

Named pipe events from Sysmon (EID 17/18) with name and PID filters; known C2 pipe names are marked. Interception: attach to an existing pipe or arm for a pipe that does not exist yet, observe or hold messages (forward, edit as hex, drop), export a session as JSON. The pipe name must be known; clients that connect while a session is starting, or that were already connected, are not intercepted.

Sysmon

Sysmon events with search, type and PID filters, and the Windows Event IDs each event corresponds to. EVENTS OVER TIME and the Sankey PROCESS → EVENT TYPE count the events of the filters, all but the time window, which the bars mark (it narrows the table): a click on a bar sets a time window (Shift+click widens it to another bar), on a legend row or a node an event type or image, each a chip in the filter bar.

ThreatScan

ThreatCheck, DefenderCheck, EMBER2024 and capa on a file. The Live Process Memory panel scans a running PID with Aether, dumps it with Process Dump, captures the host baseline or sweeps every process. SCORE HISTORY plots the scan history: Aether and Exit Capture at their evidence score against SUSPICIOUS 2 and MALICIOUS 6, the other tools in the lane "no score"; a point opens its scan in the list.

ETW

Event Log browser across 12 channels with live threat highlighting; click an event to see all fields.

Hex

Hex editor with data inspector and structure minimap. PE/ELF Analysis parses headers, sections, imports and IOC flags; Inspect shows a section's hex dump and strings.

FileMap

Byteplot, entropy and PE/ELF structure planes side by side with import/export trees; click to jump to an offset.

LitterBox

Files in the LitterBox sandbox with static, dynamic and EDR results.

Submit

Detonate a sample and follow its stages. The verdict combines EDR alerts, live memory (Aether, Process Dump, beacon scanners), the exit-time dump, network beaconing and LitterBox; VERDICT FLOW shows which findings it counted. VERDICT HISTORY above the submission history has a bar per submission in its stored verdict's colour (grey: not evaluated yet); a bar opens its results.

API

Served on port 9000, JSON. No login (keep the VM on an isolated network); state-changing requests from other web sites are refused. The full reference with all endpoints is in the README; the MCP server (mcp/server.py, 43 tools) wraps the same API.

Architecture

Web UI :9000 ──submit──▶ DetonatorAgent :8080 ──runs──▶ sample
     │    └────────────▶ LitterBox :1337 (static + dynamic)
     │
     ├──◀── alerts ── Rustinel (Sigma/YARA/IOC) · Fibratus (ETW) · Sysmon
     │
     ├──── live memory ──▶ Aether · Process Dump · HSB · BeaconEye
     │                    Exit Capture (dump at process exit)
     │
     └──── named pipes ──▶ Sysmon EID 17/18 (observe) · pipe proxy (intercept)

Data Flow

  1. Sample submitted → DetonatorAgent and/or LitterBox; exit capture armed for its image name
  2. DetonatorAgent executes it and returns the PID
  3. Rustinel, Fibratus and Sysmon record its activity
  4. Hunt-Sleeping-Beacons, BeaconEye, Aether (3 samples) and Process Dump scan the PID
  5. Sysmon network events are checked for periodic connections
  6. Sysmon pipe events of the sample's process tree are matched against the pipe catalog (C2 defaults, cross-process and system pipes, random names)
  7. All memory findings are scored together (persistence, corroboration, host baseline) and combined with EDR alerts and LitterBox into one verdict

Detection Rules

Sigma
rustinel-rules windows-advanced pack: process creation, registry persistence, tasks, services, script blocks
YARA
rustinel-rules + Elastic protections-artifacts; loaded counts are shown on the Dashboard
IOC
SHA-256, IP, domain and path matching; sample hashes are added on submission
In-memory signatures
Aether's rule files (C2 strings, reflective loading, beacon fields), mapped to ATT&CK

On ARM64 VMs

  • Aether, Hunt-Sleeping-Beacons and BeaconEye run as x64 builds under emulation; they see x64 processes reliably — which samples on ARM64 are
  • Results for native ARM64 processes are marked as limited and count only half
  • Exit dumps of emulated processes: the emulator's own executable memory is recognized and not scored
