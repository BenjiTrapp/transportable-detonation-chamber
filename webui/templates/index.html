Transportable Detonation Chamber

v1.0 — Malware Analysis & EDR Testing Platform

What is Detonation Chamber?

A pre-configured Windows 11 VM for detonating samples and watching them with several EDR-style engines at once. This web UI combines their telemetry with live-memory forensics into one verdict per detonation.

The full guide, offline: open the wiki — every page of docs/ in one file, with navigation, search, the screenshots and the diagrams, and it needs no network. The file here is dated — that is when this copy was written, which a deploy can renew; the wiki's own footer carries the date it was built and the commit it was built from. make docs on the host builds it again.

The full guide is not on this machine. Build it on the host with make docs (or .\make.ps1 docs) and deploy again: that writes static/wiki.html, the whole documentation in one file that opens without a network.

Key Capabilities

🔍
Real-time Detection
Sigma, YARA and IOC matching via Rustinel; kernel ETW behavior rules via Fibratus; Sysmon events
🧠
Live Memory
Aether, Process Dump, Hunt-Sleeping-Beacons, BeaconEye and an exit-time dump, scored by one evidence model with a host baseline
🛡
Static Scanning
ThreatCheck, DefenderCheck, EMBER2024 (ML), capa (ATT&CK capabilities), LitterBox
📊
Binary Analysis
PE/ELF parsing, packer detection, entropy, file map, hex editor; reverse engineering with rizin and rz-ghidra
📜
Log Search & Dashboards
Six log sources in one Splunk-like search, drawn as a table, pie, bars, line or Sankey, and kept as tiles on dashboards of your own

Workflow

  1. Submit a sample (Submit tab, make submit or the MCP tool tdc_submit_file)
  2. DetonatorAgent runs it; exit capture is armed first
  3. Rustinel, Fibratus, Sysmon record what it does
  4. Live-memory scanners examine the running process (1–2 minutes); if it exits, its exit dump is analyzed instead
  5. Read the verdict in Submit, then follow up in Tracing, Graph and Sysmon, or open the sample or a dump in Rizin

Process instances

Windows reuses PIDs. The UI tracks every process instance separately: 1234 is the newest process with PID 1234, 1234@1789372861 an earlier one. Alerts, events and children belong to the instance that was running at the time.

Reverse engineering

The Rizin tab opens a submitted sample, a dump, an upload or a path in rizin 0.9.1 on the VM and only reads the file: the functions, the disassembly, the control flow graph, rz-ghidra's C and the bytes all show one current address, which a click or a seek moves, with a console for rizin commands below. The server lets the console start no programs and touch no other files; renames and comments are kept in a project for the file. Each browser tab has a session of its own, three at most at a time.

Themes and card controls

✶ switches between the Telemetry and the Cyberpunk theme at once, without reloading the page: the open tab, an open detail view, filters and drilldown steps, the graph and running interception sessions stay as they are. This browser remembers the choice; without one the UI starts in Cyberpunk, the default. Both themes have the same top bar: ✶ is at its right end (and again below "? Help" in the drawer), ☰ PROCESSES opens the process list and the timeline, "…" holds the tabs that do not fit and "n/m ONLINE" lists the five services of the status row (Rustinel, Sysmon, Fibratus, Agent, LitterBox); the SERVICES ONLINE tile also counts the Detonator.

In both themes (i) beside a title explains its card, CHART / TABLE shows the numbers of a chart as a table, a click on a column head sorts the table (a second click reverses the order), and a dashboard tile opens what it counts.

Charts

The charts of the Dashboard, Alerts, Sysmon, ThreatScan and Submit tabs, of a graph node's detail and of the detonation results take the colours of the theme, and CHART / TABLE lists their numbers. A click on a bar, a slice, a legend row or a Sankey node of the Dashboard, Alerts and Sysmon charts filters by it (the dashboard opens the Alerts tab with that filter): a time range, category, rule, process, image or event type set this way shows as a chip in the filter bar, and its × takes it off. On the dashboard, 24H / 7D / 30D / ALL choose the range (ALL by default) and a drag across the bars narrows the donuts to the range drawn. In the Alerts tab a drag across the bars of OVER TIME narrows the whole tab to the bars it covers, and each click or range there that changes a filter is a step of the drilldown bar above the charts: ‹ BACK takes the last step back, a step of its path (ALL ALERTS › …) jumps back to it. Sankeys are drawn by square roots so small flows stay visible; LINEAR shows true proportions.

Tab Guide

Dashboard

Stats strip (alerts, processes, services, rules, tools; TOTAL ALERTS and PROCESSES TRACKED with 45-day sparklines), ALERT ACTIVITY (alerts stacked by severity) with the SEVERITY and CATEGORY donuts of its range, one card per service with launch buttons, Tool Updates (Check for updates looks for a newer version of every installed tool, Update all or the Update button of a row installs it; a pinned tool asks first, and while updates run a banner says that detonations, scans and uploads are paused), recent activity. A tile opens what it counts (the high / med / low counts of TOTAL ALERTS open the Alerts tab filtered by severity); a bar or a segment opens the Alerts tab filtered to it, and a drag across the bars narrows the donuts to the range drawn.

Under the header a row of pages: SERVICES is everything above, and beside it one page per own dashboard, with + NEW for another one. An own page draws its tiles, each the search it was saved from in the LOGS tab, one tile after the other — the 10 s poll leaves them alone, as does a click on the page that is already open, and the clock on a tile says how old its numbers are; leaving the Dashboard tab abandons the run, and coming back computes every tile of the open page again. Refresh in the header computes every tile of the page again, the ↻ of a tile only that one; the ⋯ of a tile opens it in LOGS, renames it, changes its form (which recomputes that tile), moves it or deletes it, and the ⋯ beside the name of the page renames or deletes the whole dashboard.

A tile keeps only its name, its query, its form and its range (the moving one of the tab or a window frozen in UTC); the numbers come from /api/logs/search each time it runs, at most 1000 rows for a chart and 20 shown rows for a table. A form the columns can no longer carry falls back to the table and says why, and a refused search shows the server's message on that tile while the others keep their numbers. At most 10 dashboards, 12 tiles each, names of 1 to 60 characters; the dashboards live in dashboards.json beside the web UI, so they survive a restart, and every change is written at once — a second browser tab on the same page is corrected by the next write.

Alerts

Every alert in one table, newest first, under charts of the alerts the filters let through: SEVERITY, OVER TIME, ENGINE and the Sankey FLOW: ENGINE → RULE → PROCESS. Filter by severity (several at once), engine and text (rule, process, description), or click a chart (here or on the dashboard): a time range, category, rule or process becomes a chip in the filter bar whose × takes it off. Drag across the bars of OVER TIME to narrow the tab to the bars the dashed box covers; the bars then divide that range anew, down to seconds for a short one. Each click on a chart and each range drawn that changes a filter is a step in the drilldown bar above the charts: ‹ BACK takes the last step back, a step of the path (ALL ALERTS › 27 Jul › 27 Jul 10:00–12:00) jumps back to it, ALL ALERTS takes every step back. What you set in the filter bar yourself (severity chips, engine, search, the × of a chip) is no step, and BACK leaves it alone; a jump from the dashboard starts a new path. The steps last until the page is reloaded. "n of m" counts the matches, and the newest 2000 of them are listed; the tab scrolls as a whole, the drilldown bar and the filter bar stay at its top. Click a row for the alert's details, a process name for its process (only processes in the process list are links).

Tracing

Per-process console: verdict, timeline by event type, process tree and alert table. Click an alert for its full raw event and Sigma match details.

Graph

Process tree around a process. Layouts: process tree, force-directed, isometric (foldable subtrees, activity icons, remote threads as bridges). The landing page lists samples and candidate processes; click a node for its detail panel, where ACTIVITY MIX shows its Sysmon activity by kind.

Pipes

Named pipe events from Sysmon (EID 17/18) with name and PID filters; known C2 pipe names are marked. Interception: attach to an existing pipe or arm for a pipe that does not exist yet, observe or hold messages (forward, edit as hex, drop), export a session as JSON. The pipe name must be known; clients that connect while a session is starting, or that were already connected, are not intercepted.

Sysmon

Sysmon events with search, type and PID filters, and the Windows Event IDs each event corresponds to. EVENTS OVER TIME and the Sankey PROCESS → EVENT TYPE count the events of the filters, all but the time window, which the bars mark (it narrows the table): a click on a bar sets a time window (Shift+click widens it to another bar), on a legend row or a node an event type or image, each a chip in the filter bar.

FIREWALL

Every connection of the chamber, bundled per process and endpoint and tagged by what is suspicious about it (IOC, beaconing, a hard-coded address, a download, a LOLBin, a DGA-like name…); the colour of a row or an arc is its most severe tag. On the left the process tree with a filter, each process with its activity and its endpoints; TDC's own processes and local addresses are groups of their own. In the middle MAP (an arc from the chamber to each public destination), LIST (a sortable table) ASN (the destinations by the organisation that owns them) and DECISIONS (the open decisions with their answers, then those of the last 24 h: when, which process, the defanged URL, what was taken and by whom, the block and the fetch with its capture). Below, the summary counts connections, blocks, open decisions and secured samples; there are no byte figures, because Sysmon records none. ALLOW / DENY blocks a process or one endpoint of it in the Windows Firewall (a rule TDC-FW-…, checked before it counts as blocked) and shows the protocol of the rule; a selected endpoint can also be blocked for every program, and KILL on a selected process ends it with taskkill /F (after a confirmation; never TDC's own). A click selects; in LOGS ▸ on the selected row, on its point of the map and above the hints opens the logs about it. ASK sets what happens when a process in the chamber fetches a file: Detonation (default) blocks it and asks, All does so for every process, Off only tags. The question is a toast on every tab, with CUT + FETCH, CUT ONLY and ALLOW and a countdown to what TDC does by itself when nobody answers (it keeps the block and fetches the file; only cuts while a block for every program stands on the address); closing the page changes nothing. What TDC decided while nobody answered stays as a toast until it is closed, and a summary says what came while the page was not looked at. CUT THE NETWORK, the red skull under the summary, is the panic button, and the ISOLATED switch in the head is the same state and the same press. It cuts without a confirmation: one outbound Block rule for every program shuts the egress in a few seconds, because a Block rule beats every Allow rule; loopback and this web UI stay reachable. Then, in the background, Windows' own outbound Allow rules (Core Networking's DNS among them) are switched off and the default set to Block, and the rule goes. The button says the stage: CUT · SECURING… while that runs, CUT · NOT SECURED when it did not get through (the band says what), ISOLATED once it is done and read back, CUT · NO FETCH where something a group policy allows cannot be switched off and the rule has to stay, and ISOLATED · OPEN when an outbound Allow rule is enabled again later. One rule decides a press: what is not confirmed closed (ISOLATED · OPEN, CUT · NOT CONFIRMED when the cut rule was not read back or, read again within 10 s, no longer stands, ISOLATED · NOT CONFIRMED) is cut again, without a question, and the band offers LEAVE ISOLATED beside it; what is confirmed closed is left. While a firewall profile is off nothing is enforced: the button is disabled and says CUT · FIREWALL OFF (or ISOLATED · FIREWALL OFF), and the off band holds LEAVE ISOLATED beside TURN THE FIREWALL ON. The card stays in view while the column scrolls. In every cut stage TDC cannot secure a sample, and the note under the button says whether it can, cannot, or whether that is not known yet. Leaving works from any stage, after a confirmation: it stops the background work and switches exactly what ISOLATED switched off on again; scripts/tdc-unisolate.ps1 on the VM is the way back if the web UI is gone. While a Windows Firewall profile is off nothing can be enforced: the switches are disabled and a red band says so, with TURN THE FIREWALL ON (after a confirmation, because it changes what the sample sees). A switch that cannot know whether it blocks, because the rules are not read yet or could not be, shows ?. HUNT FURTHER lists ready LOGS queries for the selection; SECURED SAMPLES opens a fetched file in Rizin, Hex or ThreatScan, never runs it.

LOGS

Search the PowerShell, access, MCP, NetFlow, DNS and firewall logs with a Splunk-like query: words, "phrases", field=value, AND / OR / NOT and pipes such as | stats count by tool, | top or | timechart span=5m count by source. The range buttons (15M to ALL) set the time; EVENTS OVER TIME zooms by a range drawn across its bars. A source chip searches one source (a grey one says why it has no data), a field value on the left adds field="value", and a click on an event unfolds its fields and raw text. LIVE searches again every 10 s. EXAMPLES lists searches to start from and your last ten.

The ? beside EXAMPLES opens the COMMANDS card: the whole search language in four groups, one open at a time. A click on a row adds that command to the search box instead of replacing what is there and does not search — a pipe behind the query, a term before the first pipe — so you can finish the field name and press Enter; only a source row replaces the source and searches, as a chip does. A click on the head of the card folds it away.

Over the result EVENTS, STATISTICS and VISUALIZATION switch between the matches, the table of the pipes and one chart: PIE, BARS, LINE or SANKEY, whichever the columns of the result can carry — column 0 is the name, the first column after it whose values are all numbers is the value, so a pie or bars need one of each, a Sankey two name columns, and a timechart draws as a line or as bars. What a result cannot carry stays in the row, grey, with the reason in its tooltip. A chart shows the twelve largest groups plus other (a line the series of the server) out of at most 1000 rows, and says under itself when that is less than the whole result; a click on that line adds | sort -count | head 20 and searches again (on a timechart, whose periods must not be cut, the line is only a note). SAVE at the end of the row puts the result on one of your own dashboards as a tile, with its query, its form and either the range of the tab or the window on screen.

ThreatScan

ThreatCheck, DefenderCheck, EMBER2024 and capa on a file. The Live Process Memory panel scans a running PID with Aether, dumps it with Process Dump, captures the host baseline or sweeps every process. SCORE HISTORY plots the scan history: Aether and Exit Capture at their evidence score against SUSPICIOUS 2 and MALICIOUS 6, the other tools in the lane "no score"; a point opens its scan in the list.

ETW

Event Log browser across 12 channels with live threat highlighting; click an event to see all fields.

Hex

Hex editor with data inspector and structure minimap. PE/ELF Analysis parses headers, sections, imports and IOC flags; Inspect shows a section's hex dump and strings.

FileMap

Byteplot, entropy and PE/ELF structure planes side by side with import/export trees; click to jump to an offset.

Rizin

Reverse engineering with rizin on the VM, one session per browser tab; the file is only read, nothing is written into it or next to it. OPEN ▾ lists the submitted samples, the dumps and the uploads, and takes an upload or a path in the folders the download serves; the toolbar shows the file with its format, architecture and size, the SHA256 (in full on hover) and the analysis, which starts at once (aaa, aa above 20 MB). FUNCTIONS lists the functions by address with name and size (the address on hover), filtered by name or address, and « folds it away; DISASSEMBLY shows the current function with the current address marked, calls, jumps and symbols in colour. GRAPH beside it shows the control flow graph of the function with the block of the current address marked: green edges are taken jumps, red ones the fall-through, dim ones unconditional, and loops run around the outside. Drag to move the graph, scroll or use − + to zoom and FIT to see it whole; from 200 blocks it starts as an overview without the instructions, which a click zooms into. ⇱ gives one half the whole width, the line between the halves can be dragged (← → when it has the focus, a double click puts it back), and below 1400 px of window width the two halves are tabs. A click on a function, an instruction, a jump or call target or a block, or SEEK with an address, a function or a flag name and GO, moves every view there; ◀ ▶ walk back and forth through the jumps. Once the analysis is done the tab jumps to main if there is one. While rizin works on an analysis step the toolbar says busy, and the views load once the step is over. The dock below holds the CONSOLE for rizin commands at the current address (the prompt shows it): a seek there (s, pdf @ …) moves every view, ↑ ↓ walk the history, Tab completes commands, functions and flags, and the quick commands above it run afl, pdf, pdg, iz, ii, axt and ?; the server lets no command start a program, read or write a file, open another one or debug, settings are limited to asm.*, analysis.* and bin.demangle, whole-program analysis (aa, aaa …) runs from Full analysis instead, and a refused command says why in one line. XREFS lists the references to the current address and from it, at a function's start from the whole function; STRINGS and IMPORTS come in pages, filtered on the VM, and a click jumps there and, on an import, shows its references. ═ drags the dock's height and ▾ folds it away. A right-click on a function, an instruction or a block renames the function or comments the address (an empty comment removes it), also with afn and CC in the console; both are refused (busy) until the analysis is done, because a later step could change them, are saved 3 s later in a project for the file on the VM (webui\rizin_projects\<sha256>.rzdb, made only once something is renamed or commented) and are back when the file is opened again, under any path. DECOMPILER beside DISASSEMBLY shows the function in C from rz-ghidra with the line of the current address marked, and a click on a line goes there; HEX shows 512 bytes from the current address with their ASCII, and Open in Hex tab opens the file in the Hex tab at that byte. Scrolling down a long function loads its next instructions; outside functions the disassembly stops after 2000 instructions, and a later address in SEEK reads on. A function whose decompile took too long and ended the session is not decompiled again on its own in that file: Decompile again asks once more. A file over 20 MB is analysed with aa: Full analysis runs aaa's steps one by one, the views usable between them; an analysis stops at the next step after 10 minutes and says why, what it found stays usable, and Full analysis goes on with the steps left. The same file opened in another browser tab takes the session there, and this tab offers Take it back; a session that ended (30 minutes unused, its page closed, rizin stopped) comes back with Reopen, at the same place. At most three sessions run at once, and a fourth ends the one unused longest; every command has a time limit (views 30 s, the console 60 s, a decompile 120 s), and a rizin that does not answer in time is ended without holding up the rest of the web UI. The Rizin buttons of the Submit history, Process Dump, Exit Capture, ThreatScan (its result and its history) and the Hex tab open their file here.

SYSCALLS

Aether does not look at ntdll.dll: it skips everything under C:\Windows\, and its disk comparison answers only yes or no, without a name, an address or bytes. This tab fills that gap with a baseline of what every syscall stub should look like, and names what differs. The map of every syscall of ntdll.dll and win32u.dll, one cell each in the order of its number, a band per module, comes from the NTSleuth baseline of this Windows build and view (arm64, x64). Without a scan the cells carry the baseline in one quiet tone and the map is the catalog. Choose a process, tick win32u if it is a GUI process (ntdll alone is scanned otherwise; the box is off, with the reason, when the baseline holds no win32u syscalls, as the x64 view of an ARM64 host has, and the map then has no win32u band) and press SCAN: the stubs are read from the process and each cell takes the state it was measured in, with the legend counting them. intact: as the baseline has it; hooked (file-backed module): the jump ends in a loaded module other than ntdll that a file backs, which is what an EDR does and so normal on a host with one, weak evidence, but also what a DLL the sample loaded or a legitimate DLL it overwrote in place would look like; patched: the jump ends in private memory, a section no file backs or a mapped view of a file (no loaded module, whatever file it maps), or in a core Windows module such as kernelbase.dll (a code cave), which no hooking product explains, so who owns the target tells the two apart and not the instruction. A first jump into private memory is followed when it is itself a jump, up to two relays, because MinHook and Detours hook through such a relay; the detail names the relay. A relay that leads back into ntdll is patched too, as no jump of ntdll's own goes out and back; diverged: the bytes differ but the jump is neither of those or cannot be resolved, which is never guessed at; unreadable: no stub could be read. A single deviation among the cells (some 2,000 of them in an arm64 baseline) stands out by its colour and a ring. The filter takes a name, a decimal or hex number, and the module menu narrows it to one module: cells that do not match are dimmed, not removed, so a cell stays where it is. Hover a cell for its name and number, click it to mark it; the catalog under the map lists the first 300 matches. DETAIL shows the chosen syscall with its parameters, its signature to copy, the stub bytes of the baseline and, after a scan, the bytes read with the differences marked, and links to ntdoc and WinGraph (at its root, nothing is fetched from it); Open in Rizin appears for the native view only. DEVIATIONS lists every stub of the last scan that is not intact, the loudest first, with what it added to the evidence score; Draft rule makes a signature entry and writes nothing. STUBS searches the chosen process, and its file, for syscall stubs it carries itself, a way round ntdll: each hit names its syscall, and Draft rule makes a YARA rule that names the build and view. APPLY TO THIS VM writes that rule where Rustinel reads its rules, which should load it within about two seconds (not yet verified on a VM) and is gone with the VM; DOWNLOAD FOR THE REPO gives the file to commit under rules/yara/, to keep it in version control; whether a committed rule is loaded again after a rebuild is not yet verified. Nothing is written before one of them is pressed. KNOWN HOOKS holds the hooks of this host as pairs of syscall and owning module: record them once on a host you believe is clean, and they stay on the map and in the list but no longer count as evidence. A patch is never recorded. The notices over the map say what is missing: NTSleuth not installed, no baseline for this build and view yet (it is extracted in the background), and, on an ARM64 host, an x64 view that cannot be told from the arm64 one under emulation, whose baseline is discarded on purpose and which so cannot measure emulated x64 processes; that is not a fault, and it is not the same as no baseline.

GRAPH, beside MAP, draws the import graph of C:\Windows\System32 in the map's place: what each of the binaries there (expected to be about 4,000) imports and exports, with every forwarder followed to the module that defines it. It is made on this VM from the files themselves, offline, by scripts/build-binary-graph.ps1 at provisioning; when it is missing the web UI builds it in the background and the tab says so. PATH asks one question, path to syscall, importers, imports, syscall callers, forwarders or shared dependencies, and draws the answer from left to right, one layer per hop: from an import such as kernel32.dll and WriteProcessMemory down to the syscall number of this build's baseline. EXPLORE starts at one binary and opens its neighbours node by node: EXPAND opens the modules it imports from and the ones that import it, FUNCTIONS the functions, DEPTH how many hops one click opens; at most 400 nodes are drawn, and the line above the canvas says what was left out. FIGURES counts the whole stock, and a number opens the list behind it. A solid edge is read from the binaries. The last hop from a Win32 function to its Nt counterpart is not in any binary: it comes from a hand-curated table, and it is a dashed edge marked curated, at most one per path and always the last. The step from a Zw name of ntdll to its Nt name is curated too, a naming convention that no binary states, in a path and in the syscall callers alike, and so are the rows of the table that FIGURES lists as curated transitions. A path that ends in an Nt name which ntdll or win32u exports is derived throughout. Where a table of a binary was cut short when it was read, the answer says so: the counts of the exploration and the figures are lower bounds, and any other answer is not certain. WinGraph is only linked to, never queried.

LitterBox

Files in the LitterBox sandbox with static, dynamic and EDR results.

Submit

Detonate a sample and follow its stages. The verdict combines EDR alerts, live memory (Aether, Process Dump, beacon scanners), the exit-time dump, network beaconing and LitterBox; VERDICT FLOW shows which findings it counted. API

Served on port 9000, JSON. No login (keep the VM on an isolated network); state-changing requests from other web sites are refused. The full reference with all endpoints is the API page of the offline wiki (open it here — Overview says whether that file is on this machine), and docs/api.md in the repository; the MCP server (mcp/server.py, 49 tools) wraps the same API.

GET/api/binary-graph/queryOne query over the System32 import graph, cut at 400 nodes. q=path-to-syscall follows an import (module, function) down to a syscall number. The edge from a Win32 function to its syscall is curated, the word of a hand-made table and not read from any binary: at most one per path, always the last. The other answers with curated edges are q=syscall-callers, whose step from a Zw name of ntdll to its Nt syscall is curated, a naming convention, and the list of the table's own rows, q=metric with metric=curated_transitions, each the table's word. Every other edge is derived, and a direct Nt import is derived throughout; a Zw name reaches its Nt name by a curated edge too, a naming convention that is not read from any binary. A sample outside the graph does not descend: give the DLL it imports from, such as kernel32.dll, as module. The answer has total (how many importers, chains or modules there were before the cut) and partial: true when a table it read was cut short when it was read, so a negative or a count is not certain. q=metric with metric lists what is behind one figure of /api/binary-graph/metrics: its rows as nodes, total of them (binaries, edges, api_sets_resolved, forwarders, isolated, circular_pairs, curated_transitions, most_imported, skipped, partial); an unknown figure is 400. Params: q, module, function, syscall, other, metric

Architecture

Web UI :9000 ──submit──▶ DetonatorAgent :8080 ──runs──▶ sample
     │    └────────────▶ LitterBox :1337 (static + dynamic)
     │
     ├──◀── alerts ── Rustinel (Sigma/YARA/IOC) · Fibratus (ETW) · Sysmon
     │
     ├──── live memory ──▶ Aether · Process Dump · HSB · BeaconEye
     │                    Exit Capture (dump at process exit)
     │
     ├──── named pipes ──▶ Sysmon EID 17/18 (observe) · pipe proxy (intercept)
     │
     └──── RIZIN tab ────▶ rizin + rz-ghidra, one process per file (read-only)

Data Flow

  1. Sample submitted → DetonatorAgent and/or LitterBox; exit capture armed for its image name
  2. DetonatorAgent executes it and returns the PID
  3. Rustinel, Fibratus and Sysmon record its activity
  4. Hunt-Sleeping-Beacons, BeaconEye, Aether (3 samples) and Process Dump scan the PID
  5. Sysmon network events are checked for periodic connections
  6. Sysmon pipe events of the sample's process tree are matched against the pipe catalog (C2 defaults, cross-process and system pipes, random names)
  7. All memory findings are scored together (persistence, corroboration, host baseline) and combined with EDR alerts and LitterBox into one verdict

On ARM64 VMs

  • Aether, Hunt-Sleeping-Beacons and BeaconEye run as x64 builds under emulation; they see x64 processes reliably — which samples on ARM64 are
  • Results for native ARM64 processes are marked as limited and count only half
  • Exit dumps of emulated processes: the emulator's own executable memory is recognized and not scored
